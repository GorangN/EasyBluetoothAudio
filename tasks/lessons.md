# Lessons

- When moving deployment to GitHub Actions, expose the complete documented set of deployment modes, including test installer artifacts. A default patch trigger is not the full set of options. Reuse a release version only for retries of the same workflow run; a new manual minor/major run on the same commit must honor its selected increment.

- Release versions must reserve every existing numeric release tag, including tags outside the current commit ancestry. Do not use the nearest reachable tag as the next-version baseline. Validate build/tests/installer before pushing tags, serialize releases, and make retries reuse the same commit's tag and incomplete draft.

- When animating this tray panel, derive each native frame from one fixed bottom anchor; separately animating Top and Height can make the bottom jitter. Preserve the compact snapshot during interruption and retarget from actual current bounds. Remove the entire bar identified in a supplied screenshot, and keep its requested X beside Settings without retaining duplicate close controls.

- For Settings, prefer the user's requested upward window expansion to make more content visible. Preserve its bottom edge and restore the prior compact geometry when closing; retain scrolling for limited work areas. Follow Microsoft's system-drawn window-shadow guidance instead of adding dark gradient bands to the content viewport.

- Before editing a running desktop app, compare its executable path with the checkout. A request concerning additional devices may target a newer uncommitted multi-device worktree. Preserve that implementation and resolve the target before changing an older baseline.
- When the user supplies a preferred earlier UI, restore that concrete reference closely. Keep the compact device selector, status and connection actions, with the requested `Add device` button underneath.

- A completed fresh-pairing test that still lacks the Mac audio output disproves that proposed remedy for the observed setup. Record the negative result, do not repeat the same cache-reset advice, and separate the confirmed Windows lifetime fix from the unresolved remote output failure.

- A normal Bluetooth audio setup must not depend on a developer toolchain or Terminal diagnostics on the source device. If the user declines those diagnostics, stop that path, continue available Windows-side investigation, and state the remaining compatibility gap without treating local Opened as proof of a remote audio output.

- A registered native peer may already report Opened while its OpenAsync task is still pending. A hidden startup recycle must consider every other owned native object, including enabling/opening peers, and re-check that guard in the dispatcher callback that disposes the route. The user's trace demonstrated that disposing one source can close another source on this host; application IsActive flags were insufficient protection.

- Device-scoped dictionaries and mock multi-route success do not prove simultaneous Bluetooth transport support. Verify current native state after opening, retain native failure details, and bound repeated automatic loss recovery so successful reopens cannot form an unthrottled device-to-device takeover loop.
- A settings icon must close settings when clicked again. The header X must close the current settings page before hiding the tray panel; test these user paths explicitly instead of relying only on Back/Done controls.

- Before calling a desktop feature ready, compare the running process executable path with the modified worktree and identify which solution/build the user launches. A successful worktree build does not update a separate C:/dev checkout or an installed app. Explain that distinction and provide the correct runnable build; do not treat source completion as runtime adoption.

- When the user names Anti Slop, inspect the installed plugin and resolve its exact identity. `miqdadbadjuber/anti-slop` is a specific plugin, not shorthand for design-taste-frontend, frontend-design, or impeccable. Apply its actual core and relevant skill files, state the selected workflow honestly, and complete its delivery gate. Preserve source-backed product claims and the product's own visual identity.

- When a health check is supposed to reason about one remote source, never fall back to an aggregated endpoint-level meter that can be kept alive by unrelated local audio. Prefer source- or session-specific telemetry, and return `null` when isolation is not yet trustworthy.
- For WinRT Bluetooth `\SNK` audio endpoints, do not use `System.Devices.Aep.IsConnected` as a reconnect/settle gate in either direction. It can disagree with the usable audio route. Keep physical-link presence, real-disconnect timing, and internal audio-route recycling as separate state instead of collapsing them into one timestamp.
- When reconnect fallback needs to know whether a remote audio source is still physically present, query the current `AudioPlaybackConnection.GetDeviceSelector()` results instead of re-reading `System.Devices.Aep.IsConnected`. Selector presence matches the WinRT remote-audio endpoint model more reliably for `\SNK` devices and keeps `Reconnect` vs `Connect` guidance aligned with what Windows can actually reopen.
- Do not use `x:Reference` from a tray-hosted `ContextMenu` back to the `TaskbarIcon` while that icon is still being constructed. In WPF this can create a cyclic XAML dependency and crash startup; assign `ContextMenu.DataContext` after the window has been created instead.
- For tray-hosted WPF `ContextMenu` commands, prefer binding each `MenuItem.Command` via `PlacementTarget.DataContext.<Command>` on the ancestor `ContextMenu`. It avoids both startup-time path errors against the `TaskbarIcon` object and markup-time recursion from trying to push a shared `DataContext` into the menu.
- For Hardcodet tray menus, direct event wiring can be more reliable than WPF command bindings. If tray `MenuItem` commands regress across `ContextMenu`/`TaskbarIcon` binding changes, wire `Click` handlers after window creation and invoke the ViewModel commands explicitly.
- When extracting connection cleanup into a shared teardown helper, preserve the semantics of any timing fields that distinguish an internal reset from a real disconnect. A pre-connect cleanup may need the same disposal/reset logic without rewriting the timestamp that drives reconnect backoff or settle-delay decisions.
- A zero peak alone cannot distinguish a real A2DP zombie from a user simply being idle. If silence is the only signal available, never let the monitor recycle on every threshold crossing; add a cooldown or refractory period so normal idle does not create reconnect storms.
- A cooldown on zombie recovery attempts must not suppress the first follow-up retry after a failed recycle. If the first reconnect does not restore audio, blocking all further retries for minutes strands the user in silence; only enter the long cooldown after enough failed attempts to conclude we are in a repeated-failure state rather than a one-off missed recovery.
- If recovery depends on weak heuristics instead of authoritative connection state, do not hide it behind background automation. Prefer a manual-first UX with a clear `Reconnect` action and a small, bounded auto-reconnect budget for real loss only.
- For this UI's connect-to-connected transition, do not animate only one secondary button into place while the other snaps to its final slot. The full-width `CONNECT` control must visually collapse from the midpoint while `RECONNECT` and `DISCONNECT` grow outward from that same center line, so the motion reads as one button splitting into two.
- When a UI exposes both `Connect` and `Reconnect`, keep their semantics distinct. `Connect` is the full route setup path, while `Reconnect` should only recycle the audio stream when the physical Bluetooth link still exists; exhausted fallback states must guide to the correct action explicitly.
- Any `async void` event handler that awaits work using a cancellable monitor token must catch `OperationCanceledException` for the current token/generation. Otherwise a normal stop like `StopConnectionMonitor()` can turn expected cancellation into an unhandled WPF exception.
- Any user-triggered retry loop needs its own cancellation/generation scope, not `CancellationToken.None`. If `Disconnect()` or a replacement connect request can happen while retries or fallback checks are pending, stale post-await results must be discarded before they can reapply connected or recovery UI state.
- A cancellable ViewModel loop is not enough when the underlying WinRT `OpenAsync()` cannot be cancelled. Each audio connection attempt must own a local connection plus a service-level generation, and stale completion paths must never issue a global `Disconnect()` that could tear down a newer route.
- Do not promote a plausible Bluetooth timing hypothesis into a universal settle rule without a device log that demonstrates it. Unit tests for delay arithmetic cannot prove Windows endpoint-release behavior; retain the narrowest known timing policy and validate broader delays on the affected hardware.
- For worker-to-UI recovery flows, checking cancellation before dispatch is insufficient. Re-check token/generation inside the dispatcher callback before changing UI state or globally disconnecting, because the user may cancel while the callback is queued.
- Do not collapse all "connected but silent" reports into one bug. Startup silent routes and previously healthy routes that later go silent need separate recovery rules, because startup has no prior "audio was proven healthy" signal while the idle/post-game case does.
- A one-time startup-prime recycle is not sufficient by itself for the "connected but silent on first startup" case. Fresh connects need one monitored trusted-silence recovery allowance before the first positive audio sample appears; otherwise the app can stay falsely "connected" forever until the user clicks `Reconnect`.
- If the background monitor decides to stop itself after applying fallback UI state, do not call UI-bound cleanup like `SetReconnectingState`, `OnPropertyChanged`, or command notification directly from the worker thread. Either marshal the whole stop operation through the dispatcher or separate cancellation-only cleanup from UI-state mutation.
- Treat positive audio and silent audio differently when the telemetry source is weak. A render-session match may be good enough to prove "audio exists", but its zero reading is not strong enough to prove "audio is broken"; only stronger route telemetry should drive the final `AUDIO LOST` state.
- If Windows only exposes weak session-level audio telemetry for a Bluetooth route, do not build idle detection or automatic silent-route recovery on top of it at all. Favor stable connection mechanics like startup priming and sticky reconnect for real disconnects, and leave the remaining rare "connected but silent" case to explicit user `Reconnect`.
- Inspect rendered production controls before declaring a UI ready. In WPF, implicit TextBlock styles can override inherited button foreground/font and silently hide labels or icon glyphs. Verify actual text color, one-line labels, and vector icons in rendered dark/light artifacts; layout bounds and passing builds alone do not prove visual quality.

- Keep connection policy independent of presentation: when restoring a one-device limit, preserve the accepted UI and automatically cancel/release the previous source before switching. Check other local worktrees when the active checkout predates the feature the user refers to.
- The tray panel has a fixed user-facing size: disable manual resizing and maximizing, including custom WindowChrome resize borders. Preserve the existing application-controlled settings expansion unless explicitly changed.
- The compact main source view must never scroll. Place connection/discovery errors in a bounded footer; prioritize errors over routine status and verify all actions fit the fixed window rather than adding a scrolling fallback.
- WindowChrome.CornerRadius is ignored with DWM enabled when GlassFrameThickness is nonzero. A radius-only change is insufficient; verify the production HWND region at all four corners instead of asserting XAML values alone. Read actual tool exit codes per step, and stop dependent publication commands when a prerequisite fails.
